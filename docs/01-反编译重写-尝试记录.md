# 尝试一：反编译 SWF、用 JS 重写游戏逻辑

> 2026-07-31,目标是把 `swfs/flying-ninja-cat/Flying-Ninja-Cat.swf` 重写成纯 H5。
> **最终结论:可以。** 初次使用 JPEXS 默认/激进参数时误判为无法还原;
> 改用保守的 AS1/2 执行式反混淆后,恢复出完整可读的游戏状态机,并完成了纯 Canvas H5 重制。
> 判断混淆与否见 [02-SWF-混淆判断流程.md](02-SWF-混淆判断流程.md)。

---

## 什么时候该选这条路

| 情况 | 选择 |
| --- | --- |
| AS 未混淆、逻辑清晰 | **重写**:产物是真正的 H5,可改玩法、可适配移动端、体积小(几百 KB) |
| AS 混淆,但执行式反混淆可恢复 | **先保守反编译**,再决定重写还是 Ruffle |
| 工期紧 / 要 100% 还原手感 | **Ruffle 壳**:见 `../tools/`,首屏约 14 MB wasm,但零还原误差 |
| 只想要素材(做二创、换皮) | 只跑下面的第 2 步,拿 PNG / MP3 走人 |

Ruffle 方案不是「偷懒」:它跑的就是原版字节码,美术、音效、物理、随机数全部原样。
重写方案的价值在于**可维护、可修改、可移植**——如果不打算改动游戏,重写没有收益。

## 第 1 步:读 SWF 头,确认规模

先知道舞台多大、多少帧、AS2 还是 AS3。**AS3 和 AS2 的重写难度差一个量级**,AS3 有真正的类结构,反编译产物接近可读源码。

```bash
python3 tools/scripts/swfhead.py swfs/flying-ninja-cat/Flying-Ninja-Cat.swf
```

`tools/scripts/swfhead.py`(自写,见仓库):解析 `CWS`(zlib 压缩)/`FWS`(未压缩)/`ZWS`(LZMA)签名,
输出舞台尺寸、帧率、帧数。本作是 `CWS v8, 640×480, 30fps, 50 帧`。

SWF version ≥ 9 且含 `DoABC` tag → AS3;否则 AS2。本作 v8 + `DoAction`/`DoInitAction` → **AS2**。

## 第 2 步:导出素材(这一步几乎总是成功)

```bash
java -jar tools/vendor/ffdec/ffdec.jar -export image,shape,sprite,frame,text,sound ./temp/flying-ninja-cat/work/extract/<名字> ./<文件>.swf
```

产出:

| 目录 | 内容 | 本作数量 |
| --- | --- | --- |
| `images/` | 位图(PNG,带 alpha) | 75 |
| `shapes/` | 矢量图形(SVG) | 110 |
| `sprites/` | 每个 MovieClip 的逐帧渲染 | 1193 |
| `frames/` | 主时间轴逐帧渲染(PNG) | 50 |
| `sounds/` | 音频(MP3/WAV) | 20 |
| `texts/` | 静态文本 | 9 |

**这批素材即使走 Ruffle 方案也有用**——本项目就是从 `images/100.png` 拿到忍者猫立绘当卡片图标的。

小技巧:`frames/*.png` 的文件大小能快速定位「哪几帧有内容」。
本作 `frames/21.png` 是 335 KB(游戏背景和石猫),`frames/31.png` 只有 2 KB
(空帧,靠脚本 attachMovie 搭建)。标题画面则来自运行时加载的 `swfs/flying-ninja-cat/FSAGOGUN_RES.swf`。
**大量空帧 = 游戏是脚本驱动的,重写时时间轴帮不上忙,必须读懂 AS。**

## 第 3 步:导出 ActionScript

```bash
java -jar tools/vendor/ffdec/ffdec.jar -export script ./temp/flying-ninja-cat/work/extract/<名字> ./<文件>.swf
```

同时导一份 P-code(反编译失败时的兜底,也是识破混淆的关键):

```bash
java -jar tools/vendor/ffdec/ffdec.jar -format script:pcode -export script ./temp/flying-ninja-cat/work/extract/pcode ./<文件>.swf
```

AS2 的产物结构:

- `scripts/__Packages/*.as` —— 类定义,**游戏核心逻辑在这里**
- `scripts/frame_N/DoAction.as` —— 主时间轴各帧脚本
- `scripts/DefineSprite_N/frame_M/DoAction.as` —— 各 MovieClip 内部脚本
- `scripts/DefineButton2_N/*.as` —— 按钮事件

本作的 `__Packages/` 一眼就能看出这游戏该怎么重写:

```
SetGame.as     1503 行   主游戏循环 / 状态机
MouseListener.as 983 行  输入
Delegate.as     883 行   事件绑定(标准 mx 库)
GameMode.as     820 行   模式
ItemData.as     621 行   道具表
MapData.as      536 行   关卡地图数据   ← 重写时最想要的就是这个
CoinItem.as     471 行   金币
AddNum.as       318 行   飘字
Demo.as         365 行   演示模式
JhSound.as      193 行   音频封装
```

## 第 4 步:判断能不能读(本作曾在这里误判)

打开 `__Packages/SetGame.as`,如果长这样就是**被混淆了**:

```javascript
function §\x04\x05§()
{
   set("\x03",892 % 511 * true);
   §§push("\x03");
   return eval(§§pop());
}
var §\x01§ = 585 + "\x04\x05"();
while(true)
{
   if(eval("\x01") == 966) { set("\x01",eval("\x01") - 892); §§push(true); }
   else if(eval("\x01") == 317) { set("\x01",eval("\x01") - 173); §§push(true); }
   // ...再来 40 个分支
}
```

初次导出的确能看到两层混淆叠加:

1. **控制流打散**(control-flow flattening)——真实逻辑被切碎塞进 `while(true)` + 数字跳转表,
   `\x01` 是状态寄存器。默认导出时人读不了,但 JPEXS 的 AS1/2
   执行式反混淆可以处理本作。
2. **标识符替换**——变量/方法名换成不可打印字节(`{invalid_utf8=206}{invalid_utf8=198}`)。
   即使还原了控制流,也不知道每个字段是什么。

还有第三层阴招:**常量池投毒**。同一个 action block 里放多个 `ConstantPool`,
JPEXS 静态分析会选错,于是把 `_root._url.indexOf(...)` 显示成 `_root[乱码][乱码](...)`。
详见 `02` 号文档。

### 本作真正有效的反编译参数

关键不是把所有“清理”开关全部打开,而是只启用控制流执行和常量解析:

```bash
tools/scripts/decompile-as2.sh swfs/flying-ninja-cat/Flying-Ninja-Cat.swf temp/flying-ninja-cat/work/extract/deob-safe
```

等价的 JPEXS 配置:

```text
autoDeobfuscate=true
as12DeobfuscatorExecutionLimit=10000000
autoRenameIdentifiers=false
deobfuscateAs12RemoveInvalidNamesAssignments=false
resolveConstants=true
parallelSpeedUp=false
```

结果:

- 152 份 `.as` 文件;
- `SetGame.as` 819 行、48 个方法;
- `MapData.as`、`ItemData.as`、`CoinItem.as` 均恢复为普通数组和流程;
- 核心脚本不再含 `§§push`、`§§pop`、`while(true)` 控制流分发器;
- 仍可能看到少量未引用的 `§\x01§` 全局变量,不影响主体逻辑。

为什么激进参数反而更差:开启 `autoRenameIdentifiers` 和
`deobfuscateAs12RemoveInvalidNamesAssignments` 后,JPEXS 会把仍参与间接调用的字段
当垃圾删掉。本作的 `SetGame` 会从 48 个方法缩到 28 个,属于“导出成功但逻辑被截断”。
判断反编译质量必须比较方法数量和关键类,不能只看是否还剩乱码。

## 第 5 步(未混淆时):重写

到这一步如果代码可读,剩下的就是常规移植工作:

1. **先抽数据**:`MapData` / `ItemData` 这类纯数据类直接转成 JSON,这是最省事也最保真的部分。
2. **再抽逻辑核**:游戏循环、碰撞、计分写成一个不依赖 DOM 的纯 JS 模块
   (对齐本仓库 `flypy-core.mjs` / `focus-forest/js/core.js` 的做法,方便 `node:test` 覆盖)。
3. **最后接渲染**:Canvas 2D 或 WebGL,素材用第 2 步导出的 PNG 拼图集。
4. **帧率**:SWF 是固定帧率(本作 30fps),用 `requestAnimationFrame` + 累积器做定步长更新,
   不要直接按 rAF 的间隔算物理,否则手感和原作对不上。

坐标单位:SWF 内部用 **twips**(1 px = 20 twips),从 tag 里读到的矩形要除以 20。

## 本作最终选择

完成纯 H5 重制,成品在 `../h5/flying-ninja-cat/`:

- Canvas 2D,固定 30 FPS 逻辑步长;
- 复用了原版标题、地图块、35 帧角色、金币、UI 和音频;
- 按 `SetGame.as` 恢复了跑、跳、射绳、抓绳、摆荡、旋转、坠落状态;
- 初速度 30、重力 3.5、卷轴速度 15、地图块宽 150、绳索速度 40;
- 地图模式直接来自 `MapData.as`;
- 无 SWF、无 Ruffle、无服务端成绩接口,最高分只写 `localStorage`。

Ruffle 版保留作视觉和手感基准。它仍适合要求字节级一致或时间有限的场景,
但不再是本作的唯一可行方案。

## 踩过的坑

**别用 `npm run fix:punct` 跑代码文件。** 它会把含中文的半角括号对转成全角,破坏 `foo('中文')`。

**Ruffle 在 `document.hidden` 的标签页里不出帧。** 我一度以为游戏有域名锁、花了很久做二进制补丁,
实际是 Claude 浏览器面板处于隐藏态,rAF 被节流导致画布全黑。
排查隐藏态渲染问题时,把 rAF 临时换成 timer:

```javascript
window.requestAnimationFrame = (cb) => setTimeout(() => cb(performance.now()), 16);
```

**先验证渲染器本身。** 给播放器设 `backgroundColor:'#FF0000'`,
如果舞台底色是红的说明渲染链路正常,黑屏是内容问题;底色也不出来才是渲染器问题。
这一招能在 30 秒内把「Ruffle 坏了」和「游戏没画东西」区分开。
